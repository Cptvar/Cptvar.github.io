System overview

From a changing input to an explainable result.

The platform brings together separate NBA, NHL, NFL and MLB systems on a Windows workstation. Python services, scheduled jobs and local dashboards support live observation and pregame research. SQLite stores much of the retained evidence.

  1. Collect and validate: gather source observations, identify what changed and check whether the input is usable.
  2. Preserve: retain the observation, relevant timing and calculation identity.
  3. Model and compare: run the sport’s calculations while keeping research methods distinct.
  4. Make visible: show estimates, input age, operating state and reasons for holds.
  5. Evaluate and recover: score later outcomes, investigate missing work and verify changes.

This is a conceptual map of responsibilities. It is not a claim that the four projects share one universal engine, identical controls or a single deployment process.

Give each responsibility a home.

Separate sport projects retain their own services, data, operating commands and research modules. The documented implementations distinguish collection, state construction, calculation, storage, evaluation and presentation. That separation helps locate the cause of a failure.

Source and state
Adapters turn external records into sport-specific observations. Raw evidence and revisions provide a way to revisit the interpretation.
Calculation
Model and simulation code consumes identified inputs. Research modules remain separately named rather than silently replacing an established method.
Evidence and presentation
Databases and archived records preserve the calculation trail; dashboards read and explain that state.
Operations and change history
Launchers, health checks, release manifests, patch packages, verification records and rollback instructions explain how a system is run and changed.

Examples in the retained code include separate rotation, feature, kernel, pipeline, storage and replay modules in NBA pregame work, and fit, simulation, coupling, scoring, storage and resource modules in NFL pregame work. The public site describes those responsibilities without exposing the private repositories.

A successful request is only the first check.

A source can respond with an old observation, an unexpected shape or an unresolved player identity. Collectors need bounded requests and explicit failure states; downstream work needs eligibility checks of its own.

Keep different clocks separate.

An event’s game clock, a provider’s publication time, local receipt, calculation time and forecast issue time describe different things. The documented live services retain those distinctions where the source exposes them. An unknown source timestamp stays unknown.

Do not confuse a fresh fetch with fresh information.

A newly received response can still contain an unchanged price or delayed game state. An old forecast also needs its original state and age shown, rather than appearing current because the dashboard refreshed.

Bound the external dependency.

Live-service designs use timeouts, response-size limits, concurrency limits and backoff. Local paid-API ledgers reserve expected cost and reconcile provider receipts. These local controls cannot account for every other process sharing the same provider account.

Keep enough context to explain the result later.

Documented live workflows retain source snapshots, model or code identity, relevant configuration, observations and issued results. A later outcome or correction is another record, rather than a reason to make the original forecast look better.

Use clear database ownership.

The live-service designs use SQLite write-ahead logging, one owning writer and read-only dashboard connections. This separates observation and publication from a view that merely needs to read the current state.

Replay the calculation that actually ran.

Replay uses retained inputs and the appropriate calculation identity. Versioned source and locked numerical dependencies matter: running today’s implementation on yesterday’s data is not automatically a replay of yesterday’s calculation.

Understand what a replay proves.

A matching replay supports reproducibility. It does not prove that the input was complete, that all business assumptions were correct or that a prediction was well calibrated. Coverage of the replay check itself also needs review.

A November 2026 audit found gaps as well as successful replay paths. The portfolio presents these practices as implemented capabilities with explicit limits, not a claim that every record and every module has complete replay coverage.

Related outputs should come from related events.

Generating every statistic independently can create a game that could not have happened. Shared-path simulation creates a possible game sequence, then derives related outcomes from it.

Four sports require four kinds of state.

NBA: live observation and pregame player opportunity.

Live work combines scoreboards, box scores and play-by-play with changing score and clock state. Separately, pregame research models availability, rotations and player opportunity. Shared lineup paths and team-minute constraints help keep the player view connected to the team view.

Main and challenger methods remain identifiable. The pregame and live records have their own eligibility and evaluation boundaries; a result in one is not qualification for the other.

NHL: manpower, goalies and conserved opportunity.

Hockey needs score, period, clock, shots, manpower and goalie context. The live extension uses shared future paths for shots, goals and player opportunity. Pregame research also depends on supported lineup and starter information.

Daily recovery work can quarantine affected games for specifically recognized input failures while preserving the reason and incomplete denominator. Unexpected integrity failures still propagate. A partial slate is not relabeled complete.

NFL: possession, clock and player identity.

Live football observation works with play-by-play, score, possession and time remaining. Separate pregame joint research uses quarterback context, official inactive evidence and player opportunity. Historical-situation and other challengers remain separately labeled.

The live-service design includes bounded supervisor recovery, a single owning writer and uncertain notification states after interruption. Startup arrangements and coverage differ by service; one running supervisor is not evidence that every component will recover after a reboot.

MLB: one shared baseball game.

The documented baseball architecture advances innings, batting half, outs, base occupancy, score, batting order and pitcher workload together. Batter and pitcher outcomes are derived from those shared events rather than unrelated draws.

The release record identifies an established decision model and a separate pitch-level predictive candidate. Model promotion and permission to risk capital are distinct states; installation and test success do not change that boundary. Cross-sport views and scenario research.

Research desks bring native sport outputs into a common review surface while retaining their source identity. Scenario work explores changing availability, opportunity and game conditions. One workstation makes resource choices visible.

Several useful jobs can still interfere with one another. The operating problem includes CPU, memory, storage, query latency, request quotas and the time remaining before an output becomes stale.

  • Bound work: use limited workers, calculation slots, request timeouts and explicit runtime budgets.
  • Keep research from crowding active work: background and shadow jobs need lower-priority or off-slate handling when resource pressure affects the active pipelines.
  • Make holds specific: storage pressure, exhausted quota, missing data and a stalled job are different operating states.
  • Watch actual output: a scheduled job can run successfully without producing its intended records.
  • Do not hide a backlog: an old calculation should not be represented as current merely because it completed recently.

Scheduling is primarily Windows-based, with long-running services where appropriate. The host must be awake for collection. This is not a multi-host high-availability deployment, and there is no published uptime service-level guarantee.

Explain the state before asking for action.

A useful dashboard connects the estimate with the state of the system producing it. A useful alert identifies whether the next action belongs to the operator, the source or a deliberate hold.

The documented live designs keep an outbox for eligible research notifications, apply validity and expiry checks and distinguish uncertain submissions after interruption. Provider acceptance does not prove delivery to a device, a read receipt or an executed transaction.

Private dashboard access supports review away from the desk. This public website contains selected recorded captures; it does not expose the internal dashboards or operate the machines.

A change should come with its recovery story.

The retained projects include version and source identity checks, staged verification, backups, patch packages and revert paths. Model-affecting changes are planned rather than treated as ordinary dashboard edits.

  1. Establish the starting point. Identify the source and configuration being changed, its dependencies and the relevant operating window.
  2. Preserve recovery. Keep a verified snapshot or backup before a change that depends on it.
  3. Check the intended behavior. Use suitable fixtures, replay, database checks and observed output.
  4. Verify the deployed result. A successful installer or green process alone does not establish correct operation.
  5. Retire the old recovery point deliberately. Clean up after verification, rather than removing the fallback under pressure.

The MLB release notes describe a staged test gate and a re-hashed local database snapshot for transactional recovery. That is an example of a specific implementation—not a guarantee that every project uses the same installer.

Measurement has its own architecture.

A model needs a declared reference and an eligible record. The documented workflows use prospective review points, distinct model identities and retained outcomes to separate investigation from evidence that can support a promotion decision.

As-of inputs
Use information available when the decision was issued. A later correction must not silently become an earlier input.
Whole-game context
Several forecasts from one game are related observations. They do not create several independent games.
Separate error types
Numerical simulation error differs from model uncertainty, missing inputs and structural assumptions.
Keep failures and abstentions visible
A method that only produces output on easy cases needs its coverage reported alongside its scores.
Explicit promotion
A favorable diagnostic, an installed candidate or a successful replay does not automatically replace the established model.

Audits have identified timing, coverage and lifecycle gaps in parts of the research machinery. These are reasons to improve the checks, rather than claims that a frozen protocol makes mistakes impossible.

Be precise about ownership and maturity.

My role: I direct architecture, priorities and operating rules; investigate failures; and verify changes. I use AI heavily for implementation. The work is not presented as unaided authorship of every line of code.

What is demonstrated: documented systems, original dashboard captures, operating practices, investigation records and specific verification paths. The site explains the strongest evidence without claiming that every component is complete or defect-free.

What is not established: a reliable advantage over closing betting markets, a profitable strategy, universal empirical calibration, guaranteed uptime or a fully automated system that needs no operator.

Professional context: my customer-facing enterprise support work adds escalation ownership, clear communication and coordination with Product and Engineering. The platform provides an independent setting for end-to-end systems investigation.

Public scope: this repository contains the portfolio, curated architecture notes and recorded images. It is not the source repository for the underlying sports platform.

The terms, without the shorthand.

Collector
A program that retrieves and records information from a source.
State
The information describing a game or system at a particular point in time.
Provenance
The record of where information came from and which calculation used it.
Replay
Re-running a retained calculation with the appropriate original inputs and implementation.
Shared-path simulation
Generating related outcomes from the same possible sequence of game events.
Monte Carlo error
Numerical variation from using a finite set of simulated outcomes. Reducing it does not correct a flawed model.
Calibration
Whether events assigned a particular probability happen about that often over a suitable sample.
Challenger or shadow model
A separately identified method evaluated alongside an established method without automatically replacing it.
Prospective evaluation
Defining a test before the eligible future outcomes are known.
Fail closed
Hold an output when required checks are missing or fail, instead of assuming it is safe to continue.
Write-ahead log, or WAL
A database mechanism that records changes before merging them into the main database file.
Rollback
A planned route back to a known earlier state after a change.
